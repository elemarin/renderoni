# Renderoni 1.0 CLI and Scene Composition Handoff

Status: planning document  
Current package: `renderoni@0.9.0-beta.1`  
Repository: `elemarin/renderoni`  
Audience: the next implementation agent or LLM

## Purpose

Renderoni currently has a browser editor backed by the GitHub Copilot SDK, but
it does not yet have equivalent CLI generation commands or a runtime
`Game -> Level -> Scene` composition model. This document is the implementation
contract for those changes and for the remaining work needed before the
maintainer can mark `1.0.0` ready.

The target is one shared content-generation experience:

- A human can use `renderoni editor`.
- A coding agent can use `renderoni generate` and `renderoni add`.
- Both surfaces use the same Copilot SDK request path and the same
  `.agents/skills/prompt-to-scene/SKILL.md` rules.
- Generated assets can be composed into scenes, scenes into levels, and levels
  into a game without forcing every game into one giant startup function.

Copilot CLI is not expected to generate images. The supported image workflow is
to attach a user-provided image from another source, or to generate the model
from a text prompt when no image is available.

## Current verified state

### Already present

- `renderoni editor` starts a local Models / Terrain / Levels browser tool.
- The editor calls the GitHub Copilot SDK through
  `src/editor/copilot-session.ts`.
- The editor loads the shared factory contract from
  `.agents/skills/prompt-to-scene/SKILL.md`.
- Models and terrain are expected to produce self-contained
  `() => THREE.Object3D` factories.
- The current editor supports reference image data URLs, current-vs-new
  previews, update, and save-as-new flows.
- `src/scene/inventory.ts` defines a flat `SceneInventory`.
- `src/scene/mount.ts` mounts that inventory into an engine.
- `renderoni/audio` records events for headless inspection, but does not yet
  provide a real general-purpose playback implementation.
- `renderoni/vfx` exposes screen shake and a particle type, but
  `ParticleEmitter.spawnBurst()` is a stub.
- Echoes of Blackwood already uses browser Web Audio directly and already sets
  `THREE.FogExp2`, but it does not use the Renderoni VFX particle system for
  visible atmosphere.
- Model Studio has already been removed from the Console OS source path.

### Not present

- No `renderoni generate` CLI command.
- No `renderoni add` scaffolding command.
- No shared CLI/editor generation service with CLI argument parsing.
- No `GameDefinition`, `LevelDefinition`, or `SceneDefinition` runtime API.
- No scene manager with load, enter, exit, unload, or transition lifecycle.
- No persistent-state policy when changing scenes.
- No level manifest that references multiple scenes.
- No backward-compatible adapter for existing single-scene games.
- No functional pooled particle simulation.
- No general Renderoni audio playback path.

### Existing cleanup still required

- `src/network/index.ts` still exists even though the network subpath is not
  public and the package contract treats it as removed for 1.0.
- `src/input/mobile-controls.ts` and `src/types/nipplejs.d.ts` still exist.
- `nipplejs` remains in `package.json` and `package-lock.json`.
- Input comments still claim support for gamepads and touch joysticks.
- Release documentation still mentions Model Studio and nipplejs.
- Some source comments explain implementation history or agent behavior rather
  than documenting a lasting invariant.

## Product decisions

These decisions come from the discussion that led to this handoff:

1. Renderoni is a 3D web game engine built around Three.js and Rapier.
2. The browser editor remains a supported tool.
3. The CLI must provide the same content-generation capabilities as the
   editor, using the same Copilot SDK and skill-derived prompts.
4. Images are user-supplied inputs. Renderoni does not need to generate images.
5. A model is an individually placeable object.
6. Terrain is a reusable ground, room shell, hallway segment, floor, ceiling,
   or other static environment piece.
7. A scene is a focused playable or cinematic space with its own composition,
   assets, entities, and optional camera/entry rules.
8. A level is a larger progression unit composed of multiple scenes.
9. A game is composed of multiple levels.
10. Networking, gamepad support, mobile controls, nipplejs, and Model Studio
    are out of the 1.0 scope.
11. Audio and VFX listed in the README must be real, usable features rather
    than event-only or empty stubs.
12. Echoes of Blackwood is the first integration test for scene composition,
    audio, and atmosphere.
13. The maintainer will perform final manual verification and decide when
    `1.0.0` is ready.

## Target architecture

### Hierarchy

Use the following conceptual model:

```text
Game
  -> Level
       -> Scene
            -> terrain
            -> structure
            -> decor
            -> items
            -> actors
            -> scene-local systems
```

The hierarchy must not require a game to use generated JSON. Hand-authored
TypeScript remains valid. The runtime should accept both:

- TypeScript definitions and setup functions.
- JSON manifests that reference factories and scene files.

### Proposed public types

Add types under `src/scene/` and export them through `renderoni/scene`:

```ts
export interface SceneDefinition {
  id: string;
  name?: string;
  inventory?: SceneInventory;
  setup?: (context: SceneContext) => void | Promise<void>;
  teardown?: (context: SceneContext) => void | Promise<void>;
  metadata?: Record<string, unknown>;
}

export interface LevelDefinition {
  id: string;
  name?: string;
  scenes: SceneDefinition[];
  startScene: string;
  metadata?: Record<string, unknown>;
}

export interface GameDefinition {
  id: string;
  name?: string;
  levels: LevelDefinition[];
  startLevel: string;
  metadata?: Record<string, unknown>;
}
```

The exact names can change if existing project conventions require it, but the
relationship and lifecycle semantics must remain stable.

### Scene context and ownership

Every loaded scene needs an ownership boundary:

- Track entity IDs created by that scene.
- Track scene-local systems and event subscriptions.
- Track scene-owned Three.js resources through the existing engine ownership
  machinery.
- Remove all scene entities before the scene is considered unloaded.
- Run teardown even when one scene listener or resource disposer throws.
- Do not remove persistent entities when changing scenes.

Prefer a scene context that exposes:

- `engine`
- scene ID and level ID
- a scene-local entity registration helper
- scene-local system registration
- a scene-local event subscription helper
- access to explicitly selected persistent state

Do not introduce a second simulation loop. Scene management must coordinate
with the existing fixed tick engine and dual-buffer transform pipeline.

### Lifecycle

The initial lifecycle should be deterministic and explicit:

1. `loadScene(levelId, sceneId)`: validate the definition, create its context,
   mount inventory or call setup, and register scene ownership.
2. `enterScene(sceneId)`: mark the scene active, run entry hooks, and emit a
   scene-enter event.
3. `exitScene(sceneId)`: run exit hooks, stop scene-local systems, and emit a
   scene-exit event.
4. `unloadScene(sceneId)`: run teardown, remove scene-owned entities, release
   scene resources, and clear the context.
5. `switchScene(sceneId, options)`: perform the required exit, unload/load, and
   enter sequence with a clear failure path.

Transitions such as fades are presentation concerns. They may be represented
by an option or event, but must not alter fixed-step simulation determinism.

### Persistence

Start with an explicit persistence allowlist, not implicit global persistence:

- The caller chooses persistent entity IDs or state keys.
- The scene manager preserves those values during a scene switch.
- Everything else is scene-local and is destroyed on unload.
- Player position, inventory, quest flags, and global settings should be
  possible persistent values.
- Scene-local doors, pickups, particles, and temporary effects should not
  persist unless explicitly requested.

Add tests for both preserved and discarded state.

### Inventory compatibility

Keep the existing flat `SceneInventory` format valid. Add a scene-level
wrapper or manifest format rather than breaking current JSON:

```json
{
  "version": 1,
  "id": "manor-hallway",
  "prompt": "A dark Victorian hallway",
  "elements": []
}
```

Then add level and game manifests that reference scene files:

```json
{
  "version": 1,
  "id": "blackwood-act-1",
  "startScene": "hallway",
  "scenes": [
    { "id": "hallway", "file": "scenes/hallway/scene.json" },
    { "id": "study", "file": "scenes/study/scene.json" }
  ]
}
```

The final manifest shape must be validated at runtime with explicit errors for
duplicate IDs, missing references, missing start scenes, and invalid inventory
data.

## CLI and editor parity

### Shared generation service

Extract the reusable generation path from the editor into a Node-only shared
module. It should own:

- Copilot SDK client startup and shutdown.
- Authentication/status checks.
- Model, terrain, scene, and level prompt selection.
- Shared skill-file loading.
- Image path to base64 data URL conversion.
- Fenced output extraction.
- Output validation.
- Clear errors when Copilot CLI or the SDK is unavailable.

The browser editor server and `bin/renderoni.js` must call this same service.
Do not duplicate prompt text or SDK request construction in the CLI.

### Supported CLI commands

Initial command surface:

```text
renderoni generate model "<prompt>" [--image path] [--output path]
renderoni generate terrain "<prompt>" [--image path] [--output path]
renderoni generate scene "<prompt>" [--image path] [--output path]
renderoni generate level "<prompt>" [--output path]

renderoni add model <name> [--output path]
renderoni add terrain <name> [--output path]
renderoni add scene <name> [--output path]
renderoni add level <name> [--output path]
```

Recommended options:

- `--project <path>`: project root, defaulting to the current directory.
- `--output <path>`: explicit output path.
- `--image <path>`: user-provided reference image.
- `--force`: allow replacement of an existing file.
- `--dry-run`: print validated output without writing.
- `--json`: machine-readable command result.
- `--no-preview`: skip any optional local validation that requires a browser.

The CLI must never overwrite an existing file without `--force` or an
equivalent explicit update command.

### Output rules

- `model` writes a self-contained TypeScript Object3D factory.
- `terrain` writes a self-contained TypeScript Object3D factory.
- `scene` writes a validated scene inventory JSON.
- `level` writes a validated level manifest and does not invent image content.
- `add` creates a minimal scaffold with stable IDs and TODO-free valid syntax.
- All generated files must be placed in conventional project folders:
  `models/`, `models/terrain/`, `scenes/<scene-id>/`, and `levels/`.
- The command result must print the path written and the generated type.

### Agent workflow

Update the agent skill and README with examples such as:

```bash
renderoni generate model "a weathered iron lantern" \
  --image refs/lantern.png \
  --output src/game/models/Lantern.ts

renderoni add scene study --output src/game/scenes/study
renderoni generate scene "a study with a desk and locked door" \
  --output src/game/scenes/study/scene.json

renderoni add level manor-act-1 --output src/game/levels/manor-act-1
```

The coding agent should be able to use the CLI to create content and then use
MCP to run the project and verify the result. The CLI does not need to modify
gameplay code automatically in the first release.

### Editor changes

The current editor has a `level` tab that generates a flat `SceneInventory`.
To align terminology:

- Rename the current generated-area concept to `scene` internally, while
  preserving any public compatibility needed by existing callers.
- Add a level-manifest generation path that references scenes.
- Keep Models and Terrain preview behavior unchanged.
- Add scene and level save paths using the same safe project-root boundary.
- Display the generated asset kind and destination before saving.
- Keep side-by-side previews for Object3D factories.
- Use JSON validation for scene and level outputs before enabling save.

Whether the UI shows four tabs or keeps scene generation inside Levels is an
implementation choice, but the browser and CLI must support the same four
output types: model, terrain, scene, and level.

## Make audio real

### Renderoni audio subsystem

Replace the event-only behavior in `src/audio/index.ts` with a browser-safe
implementation that has two modes:

1. Browser mode:
   - Create or attach a Web Audio context after user interaction.
   - Support procedural clips or registered `AudioBuffer` clips.
   - Support volume, loop, and position.
   - Apply master volume.
   - Stop and dispose active sources.
2. Headless mode:
   - Never access DOM or Web Audio.
   - Record deterministic `audio.play` events for tests.
   - Preserve the current inspectable log behavior.

The public API must fail clearly when a requested external clip is missing. Do
not silently claim a sound played when no source exists.

Recommended additions:

- `registerClip(name, source)`
- `play(nameOrOptions)`
- `stop(handle)`
- `setMasterVolume(volume)`
- `dispose()`

Procedural synthesis is acceptable for the 1.0 demo. Large binary assets are
not required.

### Echoes of Blackwood audio

Use the Renderoni audio API for at least:

- ambient manor drone
- thunder or low rumble
- page turn
- item pickup
- clock chime
- gate or door interaction

The existing `HorrorSoundSynthesizer` may be adapted as a procedural source,
but the game should have one clear integration path and should not maintain
two unrelated public audio abstractions.

Add lifecycle cleanup when the game is disposed or returns home.

## Make VFX real

### Renderoni particle system

Implement `ParticleEmitter` in `src/vfx/index.ts` as a bounded pooled system:

- Preallocate particle state and render instances.
- Support active/inactive particles.
- Support position, velocity, gravity/drag, color, size, lifetime, and type.
- Reuse instances instead of allocating meshes during emission.
- Update particles from fixed simulation ticks.
- Use the engine PRNG or a supplied deterministic random source.
- Expose a Three.js object that can be added to a scene.
- Dispose geometry/material resources correctly.
- Keep headless mode safe and testable without WebGL.

`spawnBurst()` must create visible state and `update()` must advance and expire
particles. It must no longer be an empty presentation method.

Recommended API shape:

```ts
const emitter = new ParticleEmitter({
  maxParticles: 500,
  textureOrStyle: 'dust'
});

emitter.spawnBurst({
  type: 'fog',
  position: [0, 1, 0],
  count: 20,
  lifetime: 3,
  speed: 0.1
});

emitter.update(dt);
```

The exact constructor can change, but the pool and lifecycle guarantees are
required.

### Echoes of Blackwood atmosphere

Add a scene-local atmosphere system with:

- slow-moving fog or dust motes in the hallway and rooms
- low opacity and PSX-compatible visual treatment
- bounded particle count
- deterministic seeded movement
- cleanup on game disposal and scene unload

Keep `THREE.FogExp2` as distance fog if it improves depth, but add visible
particles so the VFX subsystem is exercised by the game.

Add one additional visible effect such as sconce dust, a brief clock effect, or
thunder-light feedback only if it does not complicate the first integration.

## Comment and source-cleanup pass

This pass is separate from feature behavior. Its goal is to keep comments that
document public contracts, invariants, security boundaries, or non-obvious
resource ownership, while removing comments that narrate obvious code or sound
like an AI handoff.

### Keep

- Public API documentation and parameter semantics.
- Determinism rules and fixed-tick constraints.
- Ownership and disposal invariants.
- Security/path-traversal boundaries.
- Error recovery behavior that is not obvious from the code.
- Test comments that explain a non-obvious regression or platform limitation.

### Simplify or remove

- Numbered comments that merely repeat the next statement.
- Comments beginning with phrases such as "this lets", "this intentionally",
  "the editor only", or "so it never drifts" when the code is self-evident.
- Historical comments explaining why an earlier implementation was written.
- Comments describing ordinary dynamic imports or variable names.
- Marketing-style module headers that repeat README content.
- Comments mentioning AI agents when the API is general-purpose.
- Dead comments referring to removed Model Studio, networking, gamepads, or
  nipplejs behavior.

### Files requiring a deliberate comment review

1. `bin/renderoni.js`: keep command help; remove explanatory release-source
   and lazy-import narration.
2. `src/editor/copilot-session.ts`: keep public request/result docs; condense
   SDK and attachment comments.
3. `src/editor/prompts.ts`: keep the skill-loading contract; remove repeated
   explanation of why the same rules are shared.
4. `src/editor/server.ts`: keep path-boundary comments; shorten vendor serving
   and local-server explanations.
5. `src/core/engine.ts`: keep lifecycle and determinism invariants; remove
   comments that restate the code inside `step()` and cleanup loops.
6. `src/core/physics.ts` and `src/core/ownership.ts`: keep native-state and
   disposal invariants; remove conversational remediation prose where the
   diagnostic itself is sufficient.
7. `src/input/input-manager.ts`: rewrite the header after removing unsupported
   gamepads and mobile controls; keep only supported input behavior.
8. `src/audio/index.ts` and `src/vfx/index.ts`: replace placeholder comments
   with concise API/lifecycle documentation after implementation.
9. Echoes of Blackwood game/model files: remove numbered construction comments
   and keep only comments explaining puzzle-specific placement or unusual
   rendering/physics constraints.
10. Tests: preserve comments that identify a regression; remove comments that
    paraphrase the test name or assertion.
11. `.agents/skills/*.md`: do not aggressively shorten instructional
    documentation. These files are the source of behavior and are not code
    comments.

Run `rg` for `TODO`, `FIXME`, `studio`, `nipplejs`, `gamepad`, `network`, and
obsolete "not yet" claims after the cleanup.

## Verification requirements

### Automated

At minimum, all of these must pass:

```bash
npm run typecheck
npm test
npm run build
npm run build:web
npm run test:readme-examples
npm run gate:package
npm run gate:security
npm run gate:release
```

Add focused commands for:

```bash
npm run test:cli
npm run test:scenes
npm run test:audio-vfx
```

The exact script names can differ, but each requirement must have a repeatable
command in CI.

### CLI acceptance

- `renderoni --help` lists all supported commands.
- `renderoni generate model` writes valid TypeScript.
- `renderoni generate terrain` writes valid TypeScript.
- `renderoni generate scene` writes valid JSON.
- `renderoni generate level` writes valid JSON with scene references.
- `renderoni add scene` and `renderoni add level` create usable scaffolds.
- Existing files are protected unless explicitly forced.
- `--dry-run` never writes.
- Missing Copilot authentication produces a clear non-zero error.
- A user-provided image path is attached; no image-generation claim is made.
- CLI and editor produce interchangeable factory/inventory contracts.

### Scene acceptance

- A game can contain at least two levels.
- A level can contain at least two scenes.
- Scene setup and teardown run in deterministic order.
- Scene-owned entities and systems are removed on unload.
- Explicit persistent state survives a switch.
- Non-persistent scene state does not survive.
- Missing IDs and invalid manifests fail loudly.
- Existing single-scene games can run through a compatibility adapter.
- Headless stepping remains deterministic.

### Audio/VFX acceptance

- Headless audio calls produce inspectable events.
- Browser audio produces audible procedural or registered output after user
  interaction.
- Missing clip/source errors are visible and not success-shaped.
- Particle bursts activate pooled particles.
- Particles move, expire, and reuse slots.
- Fog/dust is visible in Echoes of Blackwood.
- Audio and particles are disposed when the game or scene is unloaded.
- Repeated scene switching does not leak renderers, resources, listeners, or
  particle pools.

### Manual verification

The maintainer should verify:

- Chrome desktop.
- Firefox desktop.
- Safari on macOS.
- The deployed console launcher and all supported games.
- The new two-scene composition game.
- `renderoni editor` from an npm-installed package.
- `renderoni generate` from an npm-installed package.
- A real user-supplied reference image.
- Editor update and save-as-new behavior.
- Keyboard and pointer controls after mobile/gamepad removal.
- Audio playback after the first user interaction.
- Fog/dust visibility and acceptable frame rate.

Mobile touch controls are intentionally no longer part of the supported 1.0
surface after nipplejs removal. Document that decision rather than leaving
mobile requirements in the checklist.

## Release checklist

Before declaring `1.0.0` ready:

1. All implementation phases are complete.
2. No stale Model Studio, network, gamepad, or nipplejs references remain.
3. The README matches the published package behavior.
4. The npm package contains the CLI, editor, skills, scene API, and supported
   public exports.
5. The new game proves multi-level and multi-scene composition.
6. Audio and VFX are demonstrably functional in the browser and headless-safe.
7. Automated gates pass on the supported CI matrix.
8. Manual verification is complete and recorded by the maintainer.
9. `CHANGELOG.md` contains the final 1.0 changes.
10. `package.json` is bumped to `1.0.0`.
11. A stable Git tag is created.
12. GitHub Actions publishes with the `latest` tag and provenance.
13. Verify `npm view renderoni version` and `npm view renderoni dist-tags`
    after publication.

The next implementation agent should start at Phase 0, then follow the phases
in order. Do not claim the CLI or scene hierarchy is complete until the CLI
acceptance and scene acceptance sections have passing tests and the new game
has been run.
